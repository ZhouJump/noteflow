# 乐谱识别与演奏跟踪应用 — 完整开发指引

## 1. 项目概述

开发一款以手机和平板为主要使用设备的乐谱管理与演奏辅助应用。用户可以拍摄纸质乐谱、导入相册图片、导入 PDF 或直接导入 MusicXML，将乐谱整理成独立曲谱和谱集；打开曲谱后，通过麦克风识别演奏音高，跟踪演奏进度，提供练习模式、评分模式、节拍器、纵向曲谱自动滚动和乐谱批注。

应用采用克制的拟物化设计，不要圆角不要过多自定义样式，合理组合unxtui组件来构建页面，支持离线使用，并能够安装为 PWA。

**核心原则：**

1. 浏览器端优先，乐谱图片、识别结果和用户设置默认保存在本地。
2. 原始图片需要经过处理；矫正后的页面保存。
3. 乐谱识别、演奏跟踪、评分和页面滚动彼此解耦，避免一个模块的错误导致整个演奏流程中断。
4. 先完成可验证的最小闭环，再逐步提升复杂乐谱、钢琴和自动跟踪的准确率。
5. 不以演示数据冒充真实识别结果；无法识别或无法定位的内容必须明确标记。

## 2. 技术栈

| 模块 | 技术方案 | 职责 |
|---|---|---|
| 应用框架 | Nuxt + Vue 3 + TypeScript | 页面、路由、组件、状态管理 |
| UI | Nuxt UI + 自定义 CSS | 基础交互组件与应用视觉 |
| 纸张边角检测 | quadscan | 纸张边界、透视裁切的基础能力 |
| 乐谱识别 | fschuh/homr 移植版 | 图像到音乐符号、音符和 MusicXML 的识别 |
| 音高识别 | Pitchy + Web Audio API | 实时麦克风输入、单音基频检测 |
| PDF 处理 | PDF.js | PDF 解析、逐页渲染为图像 |
| MusicXML 展示 | Verovio 或自建 SVG 渲染层 | 将 MusicXML 渲染成可显示的乐谱 |
| 图像处理 | Canvas / ImageData / WebGL（按需） | 对比度、去阴影、灰度、二值化及形变矫正 |
| 音频与跟踪计算 | Web Worker | 音高分析、跟踪搜索、评分等耗时计算 |
| 本地数据 | IndexedDB | 曲谱、谱集、图片、识别结果、设置、批注 |
| 本地文件管理 | Blob / File System Access API（可选） | 文件导入、导出及大文件处理 |
| PWA | Nuxt PWA 方案或 Workbox | 安装、离线应用壳、静态资源缓存 |

技术实施时必须核对具体库的实际能力和许可证。quadscan 主要解决边角检测与透视裁切，不应默认它能够完成任意程度的纸张去弯曲。Pitchy 主要用于单音基频检测，不能直接视为可靠的多音钢琴和弦识别器。


## 3. 产品信息架构

应用采用三个主要工作区域：

- **谱架首页**：浏览、整理谱集与独立曲谱。
- **导入工作流**：拍摄、相册、PDF、MusicXML 导入及处理。
- **曲谱演奏页**：显示乐谱、识别演奏、跟踪进度、节拍器、批注和评分。

主要路由建议：

```text
/
├── /import
│   ├── /camera
│   ├── /images
│   ├── /pdf
│   └── /musicxml
├── /scores/:scoreId
│   ├── /prepare
│   └── /play
└── /collections/:collectionId
```

具体路由可按实际页面结构调整。路由只负责界面导航，不应承担大量识别计算。

## 4. 首页：谱架与曲谱整理

### 4.1 谱架布局

首页以谱架为核心视觉隐喻，展示两类对象：

- 谱集：包含多首曲谱，有封面和名称。
- 独立曲谱：没有归属谱集的曲谱。

第一个位置固定显示一个空白曲谱卡片，作为添加曲谱入口。它与普通曲谱采用相同的卡片尺寸和视觉体系，但通过空白内容、添加图标等方式表达新增功能。

曲谱卡片显示：

- 曲谱封面或乐谱缩略图。
- 曲名。
- 可选的作曲者、调性或其他基础信息。
- 识别状态，例如处理中、已完成、需要检查。

谱集卡片显示：

- 封面：用户拍摄或从图片选择的图片，在谱集编辑对话框里设置；没有设置时使用默认的叠纸封面。
- 曲谱数量：以小角标形式压在封面右下角。
- 谱集名称：显示在卡片下方；没有封面图片时，封面内也叠一份名称（字号略大于卡片下方）。

设置了封面图片后，封面内不再重复显示名称，只保留曲谱数量角标。不必强制用户上传图片。

多页曲谱（两页及以上）在谱架上把第二页缩略图斜垫在封面下面，稍微旋转并偏移，读起来像一叠散开的纸。

### 4.2 长按拖拽整理

移动端优先使用长按触发拖拽，避免与普通点击冲突。

交互规则：

1. 长按独立曲谱卡片，进入拖拽状态。
2. 将它拖到另一个独立曲谱上，创建一个新谱集，并把两首曲谱放入其中。
3. 将曲谱拖到已有谱集上，把曲谱加入该谱集。
4. 拖动结束后，显示成功反馈，并更新谱架。
5. 支持取消拖拽；拖拽失败不应修改数据。
6. 从谱集中移出曲谱：进入谱集页，长按曲谱拖到底部“移出谱集”区域；松手在区域外则取消，不改数据。
7. 删除谱集时，应明确区分“删除谱集”和“删除谱集内的曲谱”。

拖拽时跟随指针的 ghost 使用被拖曲谱第一页的缩略图，界面不额外写操作说明文案，靠 ghost 和落点高亮表达可拖放。

桌面端可以使用鼠标拖拽，但不能依赖 HTML 原生拖拽作为唯一实现，因为触屏体验和系统行为存在差异。

### 4.3 数据关系

谱集与曲谱采用独立实体：

- 曲谱可以没有谱集。
- 曲谱最多归属一个谱集，第一版采用简单的一对多关系。
- 删除谱集默认将其曲谱恢复为独立曲谱，而不是同时删除曲谱。
- 曲谱顺序与谱集内部顺序单独保存。

### 5.1 拍摄纸质乐谱

点击首页添加曲谱卡片后进入导入入口，选择拍摄方式。

拍摄页面应支持：

- 请求摄像头权限。
- 前后摄像头切换（设备支持时）。
- 实时取景和快门。
- 拍摄后预览。
- 连续拍摄多页，不必每拍一页都返回首页。
- 删除不满意的页面、重新拍摄。
- 调整页面顺序。
- 单页重新裁切和处理。
- 结束拍摄后统一编辑曲谱基础信息。

拍摄时可叠加纸张边界辅助框，并提示用户尽量保持纸张平整、避免装订处阴影和强反光。

不要在拍摄瞬间直接覆盖原图。应保存原始拍摄结果，再生成裁切、矫正和增强后的工作副本。

### 5.2 选择相册图片

使用系统文件选择器导入一张或多张图片。移动端应兼容相册选择和文件选择行为，不能假定所有设备都会提供相同的图片选择界面。

导入后：

1. 检查图片格式、尺寸和解码结果。
2. 按用户选择顺序创建页面。
3. 进入与拍摄图片相同的图像处理流程。
4. 允许重新排序、删除、旋转和裁切。
5. 将处理结果保存为独立的页面版本。

相册图片不应默认被认为已经完成透视校正或去畸变。

### 5.3 选择 PDF

使用 PDF.js 读取 PDF 文件，并将每页渲染成图像。

要求：

- 支持多页 PDF。
- 显示页面缩略图。
- 支持选择全部页面或部分页面。
- 支持重新排序、删除页面。
- 可以设置渲染分辨率。
- 渲染后进入统一图像处理流程。
- 允许导出处理后的页面图片。

PDF 页面本身是数字排版页面时，通常不需要纸张边角检测，但仍可能需要对比度增强、去阴影或其他图像优化。

如果 PDF 只是扫描件，应按普通扫描图片处理。不要将所有 PDF 一律当作可直接提取音符的矢量文档。

原始 PDF 应保留。处理后的页面图像单独保存，并记录其来源页码及渲染参数。

当前实现：`/import/pdf` 用 PDF.js 把每页渲染成 1920 宽的 JPEG，再进入与相册图片相同的页面列表（可拖动排序、删除、识别与保存）；页数上限 30 页，渲染分辨率固定，暂未实现按页勾选与处理后图片导出。加密 PDF 只提示错误，不提供密码输入。自带曲集不走这条链路：`scripts/build-preset.mjs` 直接取公有领域的 MusicXML（钢琴来自 `musetrainer/library`，小提琴来自 `salu133445/bach-violin-dataset` 的巴赫无伴奏参考乐谱，都是 `.mxl`，缓存在 `.cache/preset-src`），纯 JS 解包后压掉标签间空白，再用 Node 版 Verovio 渲染首页 SVG，写出 `public/presets/piano` 与 `public/presets/violin` 的 manifest、各四份乐谱与预览；应用首次打开谱架时安装「钢琴经典曲集」与「小提琴经典曲集」，版面由 Verovio 现场排版，与用户自己导入的 MusicXML 完全一致。`pnpm assets` 只准备模型、ORT、Verovio 与 PDF.js，不会碰 `public/presets`。

### 5.4 直接选择 MusicXML

支持导入 `.musicxml` 和 `.xml`，并根据需要支持 `.mxl` 压缩格式。

导入后：

1. 检查文件格式与 XML 结构。
2. 安全解析 XML，不允许外部实体解析和任意外部资源加载。
3. 提取曲名、作曲者、乐器、谱表、音符、节拍、调号等基础信息。
4. 检查文件是否存在不支持的扩展或结构。
5. 建立内部乐谱数据模型。
6. 使用 Verovio 或其他渲染层显示乐谱。
7. 允许用户编辑曲名、作曲者等基础信息。
8. 保存原始 MusicXML，并支持导出。

MusicXML 导入不需要经过 HOMR，也不应要求用户提供乐谱图片。

对于 MusicXML 本身不包含的音符图像坐标，不要伪造图片定位。演奏跟踪应使用 MusicXML 的音符序列与渲染器提供的元素映射；没有原始图片时，批注直接关联到渲染后的乐谱坐标。

## 6. 图像预处理：裁切、去畸变与增强

图像处理是独立的页面级流程，不要直接写进 HOMR 推理模块。

### 6.1 处理顺序

建议的默认处理顺序：

1. 图片解码与方向校正。
2. 纸张边界检测。
3. 透视校正。
4. 弯曲检测。
5. 按需进行非刚性去畸变。
6. 去阴影与光照均衡。
7. 对比度、亮度和灰度调整。
8. 可选二值化与降噪。
9. 预览、确认与保存。
10. 将处理后的页面送入 HOMR。

处理顺序不是绝对固定的。例如，某些弯曲检测方法需要在初步增强后运行。实现时要以算法输入要求和实测结果为准，并允许配置处理管线。

### 6.2 透视校正

使用 quadscan 辅助检测纸张边角，并根据检测结果进行透视变换。

必须处理：

- 纸张边角检测失败。
- 多张纸或背景误检测。
- 边角被遮挡。
- 用户手动修正四角。
- 旋转方向错误。

检测结果应提供预览，不能默认自动检测永远正确。

### 6.3 纸张弯曲与去畸变

普通透视校正不能还原弯曲纸张。需要增加专门的弯曲检测和非刚性变形校正模块。

第一版优先研究利用五线谱几何结构的方式：

- 检测横向五线谱线。
- 估计五线谱线的曲线和局部间距。
- 判断曲率是否超过阈值。
- 对轻微弯曲尝试基于曲线的几何矫正。
- 对明显弯曲评估整页文档去畸变算法。
- 提供矫正前后对比，允许用户关闭矫正或重新调整。

不能仅把每条五线谱独立拉直后拼接整页，否则可能改变谱表间距、符号位置和音符之间的关系。

如果第一版无法可靠矫正复杂弯曲，应允许用户保留透视校正结果并继续识别，同时在页面上标记潜在风险。

### 6.4 去阴影与对比度增强

图像处理面板至少包含：

- 亮度。
- 对比度。
- 灰度模式。
- 去阴影。
- 二值化。
- 降噪。
- 恢复默认参数。
- 与原图对比。

建议实现的基础算法：

- **去阴影**：估计缓慢变化的背景光照，再进行光照均衡。
- **对比度增强**：使用线性对比度调整，后续可评估 CLAHE。
- **灰度化**：将彩色照片转为灰度图。
- **二值化**：可选全局阈值或自适应阈值。
- **降噪**：使用轻量滤波，避免破坏细小音符和升降号。

二值化不应强制应用，因为细线、符头、连音线和符号可能被破坏。默认应优先保留灰度图。

所有参数调整都必须支持预览，避免每次拖动滑块都重新运行完整的识别模型。图像处理和识别分开执行。

### 6.5 原图和处理结果的保存策略

每一页至少关联以下内容：

- 原始图片或 PDF 页面来源。
- 当前裁切与透视校正参数。
- 去畸变参数和变换映射。
- 图像增强参数。
- 处理后图片。
- 处理版本号。
- 对应的识别结果版本。

原始图片永远不被覆盖。用户修改处理参数时，重新生成处理版本；用户确认后，将选定版本作为识别输入。

如果用户之后重新裁切或去畸变，必须将旧识别结果标记为过期，避免使用旧坐标显示新图像。

## 7. 导入确认与后台识别

拍摄、相册图片和 PDF 的处理完成后，进入统一的确认页面。

用户可以：

- 拖拽页面排序。
- 删除或重新拍摄页面。
- 调整曲谱名称、作曲者及其他基础信息。
- 设置曲谱所属谱集。
- 预览原图与处理后图片。
- 选择是否进行进一步图像增强。
- 确认并开始识别。

点击确定后：

1. 保存曲谱实体和所有页面。
2. 将处理后的页面标记为本次识别输入。
3. 创建识别任务。
4. 后台执行识别，界面显示进度。
5. 允许用户离开识别页面后继续查看任务状态。
6. 识别完成后进入结果校正界面。

这里的“后台”指应用内的异步任务，不是服务器。可使用 Web Worker 执行耗时任务，任务状态保存在 IndexedDB。浏览器关闭或系统回收进程后，任务可能中断，因此要保存阶段状态，并在下次打开时恢复或重新执行。

## 8. HOMR 浏览器端移植

指定基础仓库为 `fschuh/homr`。

Python 端的作用是建立参考输出，而不是成为浏览器应用的依赖。

### 8.1 Python 基准

- 固定仓库 commit。
- 根据仓库文档安装 Python 环境。
- 使用同一批测试图片生成 MusicXML 和 visual sidecar。
- 保存模型版本、参数、耗时与输出文件。
- 验证重复运行的一致性。

### 8.2 浏览器移植

逐项检查：

- 图像预处理。
- 分割模型。
- 几何分析。
- 谱表检测。
- Transformer 编码器和解码器。
- 音乐理论后处理。
- MusicXML 序列化。
- 音符定位 sidecar。

ONNX Runtime Web 仅是运行模型的工具，不代表上述所有步骤自动可移植。每个阶段都需要记录其浏览器可用状态和对照结果。

### 8.3 识别结果与定位

识别输出至少包含：

- MusicXML。
- 音符内部 ID。
- 音高、时值、小节和声部信息。
- 音符头定位结果。
- 未成功定位的音符列表。
- 识别模型与处理版本信息。

HOMR 的可视化 sidecar 应以真实输出格式为准。原始 MusicXML 中的近似位置注释不能直接当作精确像素坐标。

图像经过裁切、透视校正或非刚性去畸变后，必须保留坐标变换映射，以便将识别坐标转换回处理后图片或原始图片。

## 9. 识别结果校正

识别完成后，显示乐谱及识别结果，用户可以检查错误。

第一版至少提供：

- 查看识别后的乐谱。
- 点击音符查看其音高、时值、小节和声部。
- 标记识别错误或定位错误。
- 修改音符的基础属性。
- 对未定位的音符手动补充位置（有图像时）。
- 重新执行识别。
- 保存修正后的结果。

应区分原始识别结果和用户修正结果。用户的修正不能被下一次识别无提示覆盖。

对于直接导入的 MusicXML，可以进入相同的乐谱检查流程，但不需要经过图像识别。

## 10. 曲谱演奏页面

演奏页面是应用的核心功能。页面需要适配手机和平板，重点保证乐谱可读、当前音符醒目、操作区域足够大。

### 10.1 页面布局

顶部：

- 返回：属于谱集的曲谱回到该谱集页，独立曲谱回到谱架；来源由曲谱的 `collectionId` 决定，刷新或直接打开也一致。
- 曲谱名称与更多操作。
- 练习 / 评分模式切换。
- 结构化乐谱的音符选中状态。

主体：

- 一份曲谱的所有页面按顺序从上往下排开，共用一条文档滚动条。
- 当前音符的三角形指示箭头。
- 音符高亮 / 选中圈。
- 跟随时随演奏进度自动滚动到当前目标。
- 用户批注层，覆盖在每一页上。

曲谱顶栏正中用紧凑的跟随 / 评分 tab 选择当前模式，按钮不占满整行；切换时结束另一边的会话，不产生成绩。

两侧（手机竖屏各约 48 px，平板可加宽）：

- 左侧：节拍器开关、节奏型（4/4、3/4、2/4）、BPM（数字与 BPM 文案是同一个按钮，点击打开对话框）、
  单行拍点指示（不换行）、声部切换（只在双手谱显示）。
- 右侧：当前模式的播放 / 暂停、停止 / 重来，以及铅笔、橡皮擦、撤销、清空。
  播放与暂停共用一个按钮；开始只启动当前 tab 的模式。
- 双手谱的左右手各用一个手形图标：右手保持原样，左手水平镜像；激活时使用与谱面箭头相同的主题色
  （右手蓝、左手红）。单谱表没有声部可筛，直接不显示手形图标。
- 两侧控件使用 `sticky` 固定在视口内，不随乐谱滚走，也不遮挡五线谱主体。

底部只保留临时状态：跟随时显示当前音与练习状态条；评分时显示当前音、准确度、进度与逐音
反馈；两者都未开始时显示点选音符的详情卡。不再设置常驻的底部工具栏。

所有确认、重命名与首次保存信息都使用 Nuxt UI 对话框，不使用浏览器原生 confirm / alert；
首次保存的标题与作曲者输入放在模态里，避免移动端输入法把页面排版顶开。

### 10.2 音符定位指示器

使用三角形箭头指示当前应演奏或正在演奏的音符。

箭头位置根据当前乐谱的音符定位数据计算，不直接依赖屏幕上的固定像素。

对于图像识别的曲谱，箭头应使用识别到的音符头坐标；对于 MusicXML，使用渲染器建立的音符 ID 与 SVG 元素位置映射。

定位失败时，应避免把箭头指向不确定的坐标。

### 10.3 自动滚动（取代自动翻页）

曲谱页采用纵向连续排版，不再翻页，也不需要在页末放置翻页触发块。

自动滚动规则：

- 练习目标变化时，目标已在视口中段就不滚；跑出中段才滚到视口中间。
- 同一行内音高不同只差几十像素，不应因此触发滚动，否则游标会在行内上下轻推。
- 图片曲谱按「页容器 + 页内音符序号」查找锚点；结构化乐谱由渲染层维护音符元素映射。
- 目标在同一页内换行时按上面的规则滚动；跨页时自然滚到下一页的对应位置。
- 用户手动滚动后，下一次目标变化再接管；不在每帧强制对齐。
- 最后一页不会滚到不存在的页面。
- 页面顺序由曲谱自身的页序决定，与滚动位置无关。

滚动位置只由当前目标与页面锚点计算，不保存屏幕像素，也不依赖翻页触发点。

## 11. 音高识别与演奏跟踪

### 11.1 麦克风音高识别

使用 Web Audio API 获取麦克风输入，通过 Pitchy 分析单音基频，并将频率转换为音符候选。

需要处理：

- 麦克风权限。
- 静音和低音量。
- 环境噪声。
- 基频置信度。
- 音高稳定性。
- 音符起音检测。
- 相邻音符重复触发。
- 八度误判。

不要每一帧都直接更新当前音符。应使用置信度阈值、连续帧确认和起音检测来减少抖动。

麦克风权限通常需要安全上下文，生产环境应使用 HTTPS 或 localhost。

### 11.2 跟踪模型

将识别出的演奏音符序列与乐谱中的预期音符序列进行匹配。

至少要维护：

- 当前预期音符索引。
- 最近检测到的音高候选。
- 当前匹配置信度。
- 最近一次成功匹配的位置。
- 跟踪失败状态。
- 当前模式与时间线位置。

第一版可以先使用音符序列窗口搜索和动态规划类算法。后续再评估动态时间规整（DTW）等方法，以适应演奏速度变化。

Pitchy 本身不是完整的乐谱跟踪器，也不是可靠的多音和弦转录器。钢琴双手演奏时，多个音同时发声，单音基频检测可能返回基频、泛音或其中一个音。必须将音高检测与乐谱匹配分离，并在真实钢琴数据上验证；不能假设每次检测都能得到完整和弦。

### 11.3 跟踪失败后的行为

**练习模式：**

- 维护最近 8 个稳定起音的按键堆栈。
- 如果这 8 个音里命中当前待演奏音符不足 3 个，且它们完整命中乐谱中其它位置连续 8 个目标，
  就把进度跳到这 8 个音之后，并滚动到新的目标。
- 匹配以完整 8 连音为单位，避免一两个重复音型导致误跳；多个匹配取离当前位置最近的一段。
- 找不到时保留最后一次可信位置，继续监听，不要随意跳到远处音符。
- 可以显示轻量提示，但不要让界面频繁闪烁。

**评分模式：**

- 不执行前后搜索纠错。
- 按评分时间线推进。
- 当预期音符未匹配时，记录该音符为 0 分。
- 不因跟踪失败暂停时间线。
- 暂停和停止仍由用户控制。

## 12. 练习模式与评分模式

### 12.1 练习模式

练习模式由演奏者的真实演奏推动进度。

- 当前指示器指向待演奏音符。
- 当检测到匹配音符时，指示器推进。
- 不匹配时不推进。
- 跟踪失败时按 8 键堆栈匹配乐谱别处的连续音型。
- 节拍器可以独立运行，但不强制驱动音符进度。
- 支持手动滚动、重置和切换声部。

### 12.2 评分模式

评分模式采用节拍器驱动的时间线。

启动逻辑：

1. 用户在顶部切到“评分”并点击开始，打开麦克风并进入“等待首音”。
2. 系统等待第一个预期音符被正确识别；在此期间结束视为取消，不产生成绩。
3. 首个音符匹配成功后，以它的实际起音时间为原点建立时间线。
4. 后续指示器按 BPM 与拍号推进；每拍长度固定为 `60000 / BPM` 毫秒。
5. 每个预期音符都产生一条评分记录；同一拍点的两只手各占一个评分音。
6. 当前时间点未匹配的音符超过容错窗口后记 0 分（漏音），时间线继续向前，不因错音停住。
7. 演奏匹配成功时，音高占 0.6、时间占 0.4：正中 100 ms 内为完美，250 ms 内为良好，
   再远记为偏早 / 偏晚；八度等价按 0.8 音高分计，错音为 0。
8. 全部音符判完后自动结束并弹出成绩；也可以随时结束，未演奏的音补齐为漏音。
9. 成绩保存 BPM、拍号、声部与逐音结果，曲谱菜单里可以查看历史评分记录。

暂停：

- 停止取帧与时间线推进。
- 保留当前进度与已判音。
- 继续后回到“等待当前音”，等下一个未判音落下后以它为新的时间原点。
- 暂停与重新等待的时长不计入演奏时长和成绩。

停止：

- 主动停止会补齐未判音的漏音并保存本次成绩。
- 还在等待首音时停止视为取消，不产生成绩。

### 12.3 评分数据

每次评分记录至少包含：

- 曲谱 ID、开始时间和结束时间。
- 使用的 BPM、拍号与声部模式。
- 总音数、完美、良好、漏音、错音、准确度与演奏时长。
- 逐音结果：全局音符序号、音名、手、判定、得分权重、节奏偏差与实际检测音高。

第一版采用简单、可解释的评分规则，后续再引入渐慢 / 渐快、声部与演奏表现评分。

## 13. 节拍器与曲谱设置

每首曲谱独立保存：

- BPM（默认 80，范围 30–240）；数字与 BPM 文案包在同一个按钮里作为触发区，点击打开对话框输入并校验，也保留加减按钮。
- 拍号：每小节拍数与拍值，优先取 MusicXML 的拍号，缺省 4/4；节拍器可切换 4/4、3/4、2/4，
  每小节第一拍重音。旧数据或导入的其它拍号统一归一到 4/4。
- 默认声部选择（左手 / 右手 / 双手）。
- 节拍器开关属于当前会话，不写入设置；重新打开曲谱时默认关闭。
- 评分使用同一份 BPM 与拍号设置，开始评分时把它们写入本次成绩快照。
- 纵向连续排版后不再保存自动翻页开关或翻页触发位置。

切换曲谱时，读取当前曲谱自己的设置，不得让一首曲谱的 BPM 意外覆盖其他曲谱。

节拍器使用 Web Audio 的前瞻调度（约 25 ms 定时、120 ms 前瞻）产生节拍，而不是依赖普通 UI 定时器。UI 定时器只负责更新拍点显示。
左侧的节拍器图标随每一拍左右翻转，停下后回到正立；翻转按拍计数而不是按拍号位置取奇偶，
3/4 时第三拍也不会和第一拍落在同一侧。

## 14. 铅笔、橡皮擦与批注

批注跟随曲谱和页面保存。

至少支持：

- 铅笔自由绘制：黑色细笔画，落笔与收笔按长度收锋，模拟手写质感。
- 橡皮擦：按住拖动时沿指针路径连续擦除，按真实屏幕半径裁掉笔画经过的部分，
  一条笔画可能被拆成多段，而不是整条删除。
- 撤销与清除；重做仍属后续工作。
- 在页面间切换后恢复批注。

批注应保存为独立的矢量笔迹，而不是直接画进原始图片。

每条笔迹应保存页面 ID、颜色、粗细和坐标点。坐标采用页面归一化坐标或稳定的页面坐标系，避免屏幕尺寸变化导致笔迹错位。

图片曲谱的批注关联到处理后页面，并根据坐标映射支持在原图和处理图之间转换。MusicXML 曲谱则关联到渲染后的页面坐标。

## 15. 声部：左手、右手与双手

当曲谱包含两个可识别的声部时，左侧提供两个手形图标；单谱表不显示声部筛选：

- 左手（图标水平镜像，主题色红）。
- 右手（图标保持原样，主题色蓝）。
- 两只都亮即双手；两只都亮时点其中一只可切到单声部，只剩一只时点另一只恢复双手。

切换声部时：

- 左手模式突出左手声部。
- 右手模式突出右手声部。
- 双手模式同时显示和跟踪两只手的目标音符。
- 非当前声部可以淡化显示，但不能破坏乐谱布局。
- 每个模式都应明确当前预期的音符集合。

声部信息优先来自 MusicXML 的 part、staff、voice 等结构；对于 HOMR 输出，需要先验证其是否保留足够的声部和谱表信息。

不能仅凭音符的高低推断左右手，因为两只手的音域可能重叠。

第一版的左手和右手模式可以用于视觉筛选和简化跟踪目标；双手实时识别的准确度必须通过真实乐器演奏测试验证。

## 16. 数据模型与本地持久化

使用 IndexedDB 保存主要业务数据，避免把大图片、音频或整份乐谱全部塞入 localStorage。

建议的实体：

### Collection（谱集）

- `id`
- `title`
- `coverImageId`（可为空）
- `coverType`（用户封面或默认封面）
- `createdAt`
- `updatedAt`
- `sortOrder`

### Score（曲谱）

- `id`
- `title`
- `composer`
- `collectionId`（可为空）
- `sourceType`（拍摄、相册、PDF、MusicXML）
- `scoreFormat`（图片曲谱或结构化乐谱）
- `recognitionStatus`
- `createdAt`
- `updatedAt`

### Page（页面）

- `id`
- `scoreId`
- `pageIndex`
- `originalAssetId`
- `processedAssetId`
- `processingConfig`
- `transformMapping`
- `recognitionResultId`

### Asset（文件资源）

- `id`
- `mimeType`
- `blob`
- `width`
- `height`
- `sourceMetadata`
- `createdAt`

### RecognitionResult（识别结果）

- `id`
- `scoreId`
- `sourcePageIds`
- `musicXmlAssetId`
- `sidecarAssetId`
- `modelVersion`
- `sourceRevision`
- `status`
- `createdAt`

### ScoreSettings（曲谱设置）

- `scoreId`
- `bpm`
- `beats` / `beatType`（拍号）
- `handMode`（`both` / `right` / `left`）
- `updatedAt`

纵向连续排版后不再有 `autoTurnPageEnabled` 与 `pageTurnTriggers`；节拍器是否开启属于会话状态。

### Annotation（批注）

- `id`
- `scoreId`
- `pageId`
- `strokes`
- `updatedAt`

### PracticeSession（练习记录）

- `id`
- `scoreId`
- `mode`
- `startedAt`
- `endedAt`
- `bpm`
- `results`

所有实体使用稳定 ID。数据库升级必须提供版本迁移策略，并处理浏览器存储空间不足、数据损坏和导入失败。

## 17. 后台任务与状态管理

将图像处理、HOMR 推理、音高分析和评分分别封装成独立模块。

建议的识别任务状态：

```text
queued
  ↓
preprocessing
  ↓
recognizing
  ↓
postprocessing
  ↓
completed

任意阶段可进入 failed 或 cancelled
```

界面需要：

- 显示当前阶段。
- 显示进度（只有可以准确计算时才显示百分比）。
- 允许取消尚未完成的任务。
- 保存失败原因。
- 识别失败后允许重试。
- 识别完成后提供查看结果入口。

Web Worker 负责耗时计算，主线程负责界面和交互。浏览器关闭后无法保证任务一直运行，因此应记录阶段状态，重开时检查未完成任务并提供恢复或重新执行能力。

## 18. PWA 与移动端体验

应用必须支持安装为 PWA。

要求：

- 提供 Web App Manifest。
- 提供应用图标、名称、主题色和启动页配置。
- 缓存应用壳和必要的静态资源。
- 可在离线状态下浏览已保存的曲谱。
- 已下载的模型在本地可用时，允许离线执行对应推理。
- 麦克风和摄像头使用时，显示明确的权限和状态提示。
- 网络断开不应导致本地曲谱消失。
- 安装后能够从主屏幕启动。

当前实现：`public/manifest.webmanifest` 的应用名是 `NoteFlow`，网页标题仍带「· 乐谱识别与演奏辅助」；
`display_override` 首选 `window-controls-overlay`。`PageHeader` 带 `data-app-titlebar`，在 WCO 模式下按
`env(titlebar-area-x/width)` 左右留白并设置 `app-region: drag`，按钮、链接和输入框为 `no-drag`。
应用每次启动都会询问安装，但先等 `beforeinstallprompt` 再决定话术。Chrome 与 Edge 在页面加载后几百毫秒就派发
（Edge 152 全新 profile 实测 200–400ms，没有 Service Worker 也会发，`Page.getInstallabilityErrors` 为空），
Safari 与 Firefox 不发；所以已经有事件时 0.8 秒后弹出并给一键安装，没有事件时等 2.5 秒再给浏览器菜单或 iOS
分享菜单步骤，避免把可安装误报成不支持。手动步骤弹出后事件才到时，对话框就地换成安装按钮；用户已关掉手动步骤
的，事件到达时再问一次。已安装或写入 `noteflow:install:off`（自动化验收）时跳过。

注意：PWA 安装能力不等于后台任务永久运行。操作系统可能挂起或终止应用，耗时识别任务必须支持状态保存与恢复。

移动端重点测试：

- iOS Safari / 安装后的 Web App。
- Android Chrome / 安装后的 PWA。
- 手机竖屏与横屏。
- 平板横屏演奏。
- 摄像头权限、麦克风权限。
- 大尺寸 PDF 和高分辨率图片的内存使用。

## 19. 视觉与交互规范

整体风格采用克制的拟物化设计，以谱架、纸张、封面和乐谱为视觉主体。

设计原则：

- 谱架卡片有轻微的层次、纸张或封面质感。
- 不使用过重的阴影、复杂渐变或过度装饰。
- 识别状态、演奏位置和评分状态需要清楚，但避免大量高饱和颜色。
- 演奏页面的乐谱优先级高于工具栏。
- 关键操作区域适配触摸，避免过小的点击目标。
- 长按拖拽必须有视觉反馈。
- 图片处理参数调整必须提供实时或准实时预览。
- 所有耗时操作都有明确状态，避免用户误以为应用卡死。

### 19.1 界面文案

界面文案面向演奏者，不面向开发者。每句话回答“现在怎么样、接下来做什么”，不解释实现。

- 不出现实现细节：Worker、模型名（SegNet、Transformer）、IndexedDB、跨源隔离、渲染、编码、地址栏这类词不上界面。
- 错误提示不拼原始异常文本。技术细节写进 `console`，界面只给一句能行动的话。
- 用“这台设备”“谱架”“识别”“保存”这类日常说法，不用“本机”“实例”“句柄”等术语。
- 专业名词只保留乐理与文件格式：BPM、拍号、休止符、MusicXML、PDF。
- 流程提示先说结果或好处，再给步骤；同一个动作在各页使用同一个动词，按钮与标题保持一致。

## 21. 开发阶段与验收标准

### M1：基础工程与本地数据

完成 Nuxt 工程、PWA 基础配置、IndexedDB 数据模型、谱架布局和曲谱实体。

验收：能够创建曲谱和谱集、在本地保存，并完成基础拖拽整理。

### M2：统一导入流程

完成拍摄、多图片导入、PDF 导入和 MusicXML 导入。

验收：四种入口都能生成正确的数据对象；图片和 PDF 能按页管理；MusicXML 不需要经过 HOMR。

### M3：图像处理

完成 quadscan 集成、透视校正、手动裁切、去畸变原型、对比度增强、去阴影、处理结果保存和坐标映射。

验收：原图不被覆盖，处理后的页面可导出；识别使用明确指定的图像版本。

### M4：HOMR 浏览器移植

建立 Python 基准，完成浏览器模型推理、后处理和 MusicXML 输出。

验收：至少一条真实浏览器识别链路运行成功，并与 Python 基准对照。没有完成的阶段明确列出，不得用模拟输出代替。

### M5：识别结果校正与乐谱展示

完成结果解析、音符定位、MusicXML 渲染和基础人工校正。

验收：图片识别结果和直接导入的 MusicXML 都能显示乐谱，并正确处理各自的定位方式。

### M6：音高识别与练习模式

完成麦克风采集、Basic Pitch 复音检测（模型拿不到时退回 Pitchy 单音检测）、局部搜索和练习模式跟踪。

验收：真实演奏时能推进当前音符，跟踪失败时能按 8 键堆栈匹配乐谱别处并跳转，
不可信匹配不会导致任意跳转。

### M7：节拍器、纵向曲谱与自动滚动

完成 Web Audio 节拍器、每曲谱独立的 BPM / 拍号设置、BPM / 节奏型对话框、多页纵向排版、
跟随暂停/继续，以及目标跨页时的自动滚动。

验收：节拍器按 BPM 稳定发声并显示拍点；暂停停住游标与节拍器、恢复后继续；
所有页面从上往下排列，目标跨页时文档滚到对应音符；BPM 与声部按曲谱持久化。

### M8：批注、声部与移动端完善

完成铅笔、橡皮擦、撤销、清空、左手/右手/双手切换（仅双手谱）、两侧控件栏与手机布局优化。
橡皮按住拖动时沿路径连续裁切笔迹。

验收：批注以归一化坐标持久保存，刷新后恢复；曲谱设置独立；声部切换会重建跟踪目标，
不会沿用切换前的半只手状态。

### M7-评分：评分模式（已完成）

完成 BPM 驱动的时间线、首音锚定、逐音符评分、暂停 / 继续 / 结束，以及成绩与历史记录落库。
继续评分后回到等待当前音，以它为新原点。

验收：八个四分音符 @ 60 BPM 的假麦克风输入能弹出成绩，逐音结果写入 `runs` store；
`check:scoring` 覆盖纯逻辑 21 项与浏览器 13 项。

### M9：PWA、离线与发布准备

完成安装、静态资源缓存、离线查看、任务恢复和许可证审查。

验收：安装后的应用可在离线状态下使用已保存曲谱，文档完整，关键流程有自动化或可重复的人工验收步骤。

这能尽早验证两个最大风险：HOMR 能否在浏览器端可靠运行，以及实际乐谱图像的音符定位能否支撑后续的演奏跟踪。多音识别与非刚性去畸变则需要独立的测试和迭代，不应假定现有库能够直接解决全部问题。
